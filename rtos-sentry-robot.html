01 / Overview

What it does and why I built it

I wanted a project that forced me past Arduino's single loop() model and into real concurrency — tasks with priorities, an ISR that has to hand off work safely, and shared state that has to be protected instead of just hoped about.

SentryBot follows a black line on a white surface using a 5-sensor IR array, while an ultrasonic sensor watches ahead for obstacles. Rather than reading every sensor and computing motor output in one loop, the firmware runs four FreeRTOS tasks: LineSenseTask (highest priority, reads the IR array and computes a steering correction), ObstacleTask (polls the ultrasonic sensor and can override steering), MotorTask (owns the motor driver and consumes commands from a queue), and TelemetryTask (lowest priority, streams state over serial for debugging).

A hardware interrupt on a front bumper switch can halt both motors immediately regardless of what any task is doing — that path deliberately bypasses the queue system entirely, since a physical collision needs a faster response than task scheduling can guarantee.

Four tasks, one queue, one interrupt

04 / Firmware

Task setup and the direct-cut ISR

Simplified from the actual source. The bumper ISR sets motor PWM to zero directly rather than posting to the queue, so a collision doesn't wait on scheduling.

main.cppC++ / FreeRTOS
// task creation, pinned to core 1
xTaskCreatePinnedToCore(LineSenseTask, "line",     2048, NULL, 3, NULL, 1);
xTaskCreatePinnedToCore(ObstacleTask,  "obstacle", 2048, NULL, 2, NULL, 1);
xTaskCreatePinnedToCore(MotorTask,     "motor",    2048, NULL, 3, NULL, 1);
xTaskCreatePinnedToCore(TelemetryTask, "telem",    2048, NULL, 1, NULL, 1);

// bumper interrupt: bypasses the queue entirely
void IRAM_ATTR onBumperHit() {
  ledcWrite(MOTOR_L_CH, 0);
  ledcWrite(MOTOR_R_CH, 0);
  collisionFlag = true;  // picked up by MotorTask next cycle
}

// MotorTask: only source allowed to drive the H-bridge
void MotorTask(void* pv) {
  MotorCmd cmd;
  for (;;) {
    if (xQueueReceive(cmdQueue, &cmd, portMAX_DELAY)) {
      if (!collisionFlag) applyMotorCmd(cmd);
    }
  }
}
05 / Build Log

How it came together

Single-task line follower

Started with the simplest possible version — one loop reading the IR array and driving motors directly — to validate the sensor thresholds and steering math before introducing any concurrency.

Split into FreeRTOS tasks

Refactored the working loop into LineSenseTask and MotorTask connected by a queue, which immediately surfaced a race condition where both tasks touched the motor driver directly — fixed by making MotorTask the sole owner of the H-bridge.

Obstacle task + priority tuning

Added ObstacleTask and spent most of this stage adjusting task priorities and periods after the robot's steering became visibly jittery under the default round-robin scheduling.

Bumper ISR + telemetry

Added the hardware interrupt for the bumper switch as a hard override outside the task system, then bolted on TelemetryTask last since it was purely for observing the other three.

07 / Challenges

What actually went wrong

Issue — two tasks driving one motor

Early on, both LineSenseTask and ObstacleTask wrote to the motor driver directly, and under obstacle interrupts the robot's steering would visibly stutter. The fix was structural: neither task touches the H-bridge anymore, they only post MotorCmd structs to a queue that MotorTask alone consumes.

Issue — ISR doing too much work

My first version of the bumper ISR called a full stop-and-log function, which is unsafe inside an interrupt context. Trimmed it down to two register writes and a flag, with the actual logging deferred to TelemetryTask.

08 / Future Improvements

What I'd do next

  • Add a PID controller to LineSenseTask instead of the current proportional-only steering correction.
  • Move telemetry off serial and onto a queue-backed BLE characteristic for wireless debugging.
  • Add a mutex-protected shared state struct so TelemetryTask can read task status without touching the command queue.
